# Настройка хоста для семейства скиллов PDCA

Установка скилла копирует только инструкции. PDCA-скилл **называет роли** — агентов он не
создаёт и моделей не задаёт, — поэтому цикл поедет только после того, как хост (OpenCode) даст
этих агентов, разрешит дешёвому primary их диспетчеризовать и разрешит вложенную делегацию.
Эта страница — недостающий install-чеклист: скиллы → агенты → оркестратор → глубина делегации →
права → привязка моделей → перезапуск → проверка. Она host-агностична; команды в качестве
референсного адаптера — OpenCode V2, а соответствия для Claude Code, Codex и кастомных хостов
(`dsh`, …) даны рядом.

Без этого цикл не падает громко: он либо уходит в плоский primary (с записанной строкой
`Notice:`), либо упирается в resource blocker на первом же диспетче.

## 1. Что скилл ждёт от хоста

Роли — это **имена субагентов**. У каждого скилла семейства есть своя таблица
(`## Roles and host requirements`); здесь она только сведена вместе.

| Скилл | Кого диспетчеризует | Ассеты ролей в поставке |
|---|---|---|
| `pdca` | `pdca-scout`, `pdca-planner`, `pdca-executor`, `pdca-check`, `pdca-escalate`; драйвер — primary (обычный режим) или `pdca-orchestrator` (автономный) | `assets/opencode-agents/*.md` (6 файлов — канонический общий набор) |
| `pdca-coder` | `pdca-scout`, `pdca-planner`, `pdca-executor`, `pdca-check`, `pdca-escalate`, `pdca-security-auditor` | `assets/opencode-agents/*.md` (7 файлов — 6 байт-в-байт зеркал + специалист) |
| `pdca-dotnet` | как `pdca-coder`, плюс необязательные специалисты `dotnet-*` | `assets/opencode-agents/*.md` (7 файлов — 6 байт-в-байт зеркал + специалист) |
| `pdca-collection` | всё вышеперечисленное по задаче, плюс драйвер `pdca-orchestrator` | `assets/opencode-agents/pdca-orchestrator.md` (зеркало) |
| `pdca-incremental` | `pdca-planner`, `pdca-executor`, `pdca-scout`, `pdca-check` по шагам, плюс драйвер `pdca-orchestrator` (цикл шага добавляет `pdca-escalate`) | `assets/opencode-agents/pdca-orchestrator.md` (зеркало) |

Все поставляемые id агентов несут префикс `pdca-` и **одинаковы у базы и у оверлеев**: скилл никогда
не перехватит уже существующих у хоста `planner`, `coder`, `scout`, `check` или `escalate`.

Агенты несут только **идентичность, тир, полномочия и output-контракт**; знание решений
(маршрутизация, контракты фаз, приёмка) живёт в скилле и загружается вместе с ним. Драйвер в частности
никогда не классифицирует задачу — он загружает контракт формы и специализированного скилла, объявленных
планом.

Драйвер **`pdca-orchestrator` поставляется в `assets/opencode-agents/` каждого скилла** (один и тот же
файл, поэтому есть при любой установке). Любому скиллу также нужен primary на cheap-тире для
**автономного** режима: тир берётся из эффективного тира профиля хоста, а не из имени агента.
Medium/strong primary (например `architect`) автономный цикл **не** запускает: он делает явный handoff
дешёвому primary (`build` по умолчанию), сохраняя задачу, статус-файл и ссылки `.pdca/`. В **обычном**
режиме primary сам ведёт цикл и просит пользователя одобрить план до DO; это разрешено в пределах прав,
которые профиль реально даёт. Если профиль явно запрещает primary управлять циклом, это заявленный
блокер, а не повод расширять права.

## 2. Поставить скиллы

Ставьте каталог скилла целиком: `SKILL.md`, `assets/` и `scripts/`, если скилл их поставляет.
Корень скиллов зависит от хоста:

| Хост | Корень скиллов |
|---|---|
| OpenCode | `~/.config/opencode/skills/` (пользователь), `.opencode/skills/` (проект) |
| Claude Code | `~/.claude/skills/` (пользователь), `.claude/skills/` (проект) |
| Codex | `~/.codex/skills/` (или `$CODEX_HOME/skills`), проект `.agents/skills/` |
| кастомный (`dsh`, …) | корень скиллов хоста; тот же layout `<root>/<id>/SKILL.md` |

Сборки Codex читали больше одного корня скиллов (проект: `.agents/skills/`, `.codex/skills/`;
пользователь: `$CODEX_HOME/skills`, `~/.agents/skills`). Скилл становится доступным из любого
документированного корня — проверяйте, что он виден в списке доступных скиллов сессии, а не
предполагайте путь.

Команды ниже — референсный адаптер OpenCode; для другого хоста замените корень назначения.

```sh
npx skills add AlexeyShirshov/skills@pdca-dotnet -g -y
```

По одной команде на скилл (`pdca`, `pdca-coder`, `pdca-dotnet`, `pdca-collection`,
`pdca-incremental`); `-g` — для всех проектов, без него CLI ставит в текущий проект.
`pdca` — единственный вход и весь цикл; два оверлея и две формы по-прежнему ставятся отдельно
для явного вызова. Модели показывается только `pdca`: у остальных скиллов стоит
`metadata.opencode/autoinvoke: false`, поэтому они загружаются лишь по явному id (`@pdca-dotnet`)
или когда их выберет PLAN базы — выбрать контракт «по фразе» модель не может. Из чекаута
(пути от корня репозитория):

```sh
cp -r skills/pdca* ~/.config/opencode/skills/
```

Для семейства PDCA глобального каталога достаточно — OpenCode сканирует
`~/.config/opencode/skills`. Пак `skills-keep.txt` + `curate-skills.mjs` нужен только для скиллов
в отдельном `skills`-источнике; если семейство живёт там, добавьте пять id в список и пересоберите
пак.

Хелперы из `scripts/` установленного скилла — **источник** рантайм-копий (`pdca` и `pdca-coder`
поставляют `pdca_cost.py` и `plan_lint.py`; `pdca-dotnet` дополнительно `validate_inner_loop.py` и
`pdca_evidence.py`). Перед первым запуском хелпера
`pdca-executor` кладёт их в `.pdca/scripts/` проекта байт-в-байт копиями, и каждая команда идёт от
корня проекта (`python3 .pdca/scripts/<helper>.py …`); из установленного каталога скилла хелпер не
запускается никогда. Сам workspace `.pdca/` цикл создаёт в проекте, где идёт. `tests/` и
генераторы диаграмм в `assets/diagram/` нужны только для разработки, не для рантайма.

Долговечную запись держите в индексе, локальный побочный продукт — вне его. Один раз, в проекте,
где идут циклы:

```gitignore
# PDCA: статус-файл — долговечная запись; свидетельства и хелперы локальны.
# Числовой `rv<k>` под id задачи/коллекции покрыт на любой глубине (и вложенные items).
.pdca/*/**/rv[0-9]*/
.pdca/scripts/
```

## 3. Поставить агентов-ролей

Агенты — это **определения субагентов хоста**. Поставляемые `assets/opencode-agents/*.md` несут
OpenCode-frontmatter (`mode: subagent`); общие ассеты несут V1-карту `permission:` и эквивалентный
V2-список `permissions:` поверх переносимого промпта роли; другой хост сохраняет тело и транслирует
frontmatter:

| Хост | Корень агентов | Frontmatter |
|---|---|---|
| OpenCode | `~/.config/opencode/agents/`, `.opencode/agents/` | как есть |
| Claude Code | `~/.claude/agents/`, `.claude/agents/` | `name`, `description`, `tools`; права — через allowlist инструментов, `mode`/`permission` убрать |
| Codex | `$CODEX_HOME/agents/` (обычно `~/.codex/agents/`), `.codex/agents/` | один TOML-файл на роль: `name`, `description`, `developer_instructions` (§3) |
| кастомный (`dsh`, …) | корень агентов хоста | тело оставить, frontmatter адаптировать |

Если у хоста нет субагентов, цикл идёт по flat-primary fallback, описанному в скилле.

OpenCode находит агентов в `~/.config/opencode/agents/<name>.md` (глобально) и
`.opencode/agents/<name>.md` (в проекте). ID агента даёт путь (вложенный путь становится частью ID:
`.opencode/agents/team/reviewer.md` → `team/reviewer`).

```sh
# pdca
cp skills/pdca/assets/opencode-agents/*.md ~/.config/opencode/agents/

# либо pdca-coder / pdca-dotnet
cp skills/pdca-coder/assets/opencode-agents/*.md ~/.config/opencode/agents/
```

> **Один общий набор, генерируемые зеркала.** У шести общих ролей (`pdca-planner`, `pdca-executor`,
> `pdca-check`, `pdca-escalate`, `pdca-scout`, `pdca-orchestrator`) **один авторитетный источник**:
> `skills/pdca/assets/opencode-agents/`. `pdca-coder` и `pdca-dotnet` поставляют байт-в-байт
> копии этих шести (frontmatter, тело и права), а `pdca-collection`/`pdca-incremental` — только
> такую же копию `pdca-orchestrator`. Проверка и перегенерация:
> `python3 skills/pdca/scripts/sync_role_assets.py --check` (или `--fix`); явный allowlist никогда
> не трогает `pdca-security-auditor` и рукописные файлы. `pdca-security-auditor` — единственная
> роль coder/.NET, которая отличается намеренно: это специалист-сборщик фактов, а не одна из общих
> шести. Поэтому ассеты `pdca`/`pdca-coder`/`pdca-dotnet` дают те же шесть ролей, а пакет формы
> (`pdca-collection`/`pdca-incremental`) добавляет только оркестратор и ставится вместе с одним из
> шестиролевых пакетов.

**Исполняемая версия поставляется вместе со скиллом.** У `pdca` есть промпт установки агентов —
`assets/install-agents-prompt.md` (после установки:
`<skills-root>/pdca/assets/install-agents-prompt.md`), поэтому он приезжает вместе с `npx skills add`
и чекаут не нужен. Отдайте его сессии, которой можно писать конфиг хоста: он разложит те же файлы,
затем выполнит §8 — привязку моделей по тирам — и проверит и то, и другое. Preflight самого скилла
выдаёт пользователю ровно этот промпт, когда роль не разрешается (§1, §10), так что копировать файлы
руками не нужно.

> Промпт, а не скрипт установки, из-за §8: id моделей живут в профиле хоста — JSONC с комментариями,
> собранный из нескольких мест, и это могут быть только id, которые хост действительно предлагает.
> Скопировать байты — механически; выбрать модель по тиру, не выдумав id и не уничтожив комментарии, —
> нет.

### Claude Code: `tools` и `model` вместо карты прав

Claude Code сохраняет тело роли и транслирует frontmatter (`name`, `description`, `tools`,
`model`). Карты прав и профильного `agents`-блока там нет, поэтому `tools` — вся граница, а модель
привязывается в самом файле:

- `pdca-planner` и `pdca-check` получают `Read, Grep, Glob` — без шелла и без инструментов записи;
- `pdca-executor` — `Read, Write, Edit, Bash, Glob, Grep`;
- `pdca-scout` сохраняет `Bash` ради своих фиксированных read-only литералов, потому что `Bash` нельзя
  ограничить до одного агента; поэтому `pdca-escalate` собирает факты через `pdca-scout`, а не своим
  шеллом;
- `pdca-orchestrator` — `Read, Agent, Skill`, без записи и без шелла;
- `model:` принимает `sonnet`, `opus`, `haiku`, `fable`, полный id модели или `inherit` — это и есть
  привязка по тиру в Claude Code, поэтому обновление обязано её переприменять, а не терять.
  `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` перекрывает любое поле `model:` — проверяйте его прежде, чем
  утверждать, что привязка работает.

`Agent` (до v2.1.63 — инструмент `Task`; старое имя работает) — инструмент запуска субагентов, он
должен быть в определениях `pdca-orchestrator` и `pdca-escalate`. Внутри субагента allowlist
`Agent(type)` игнорируется, поэтому список детей драйвера остаётся правилом уровня промпта. Таблица
инструментов по ролям и правила трансляции файла поставляются в промпте внутри скилла.

### Codex: один TOML-файл на роль

Codex принимает кастомных агентов как отдельные TOML-файлы, по одному на роль, в `$CODEX_HOME/agents`
(обычно `~/.codex/agents`) или `<проект>/.codex/agents`. Обязательны три ключа: `name`,
`description`, `developer_instructions`. Первые два берутся из поставляемого frontmatter, третий —
тело роли без frontmatter: экранируйте обратные слэши и `"""` внутри TOML-строки, остальное
сохраните байт-в-байт. Идентичность — `name`; совпадение имени файла с ним лишь соглашение.

- **тиры** — `model` и `model_reasoning_effort` в каждом файле. Файл перекрывает дефолты `[agents]
  default_subagent_model` / `default_subagent_reasoning_effort`, а роль без обоих наследует
  родительскую сессию. Тиры реальны ровно настолько, насколько привязаны по ролям; один дефолт
  `[agents]` их схлопывает.
- **возможности** — документированные рычаги в файле агента: только feature-переключатели
  (`features.shell_tool`, `features.apps`, `features.plugins`, `features.memories`,
  `features.request_permissions_tool`) и переключатели скиллов. `pdca-planner`, `pdca-check` и
  `pdca-orchestrator` ставят `features.shell_tool = false`. Переключателя правок **на агента нет**,
  поэтому read-only для любой другой роли — правило уровня инструкции.
- **наследование** — `sandbox_mode`, `approval_policy`, `model_provider` и `mcp_servers` в файле
  агента игнорируются: агент берёт значения родительской сессии. Не пишите их.
- **делегация** — `[agents] enabled` (по умолчанию `true`), `max_concurrent_threads_per_session`
  (легаси-алиас `max_threads`) и два дефолта выше. В опубликованном справочнике конфигурации ключа
  глубины нет; некоторые сборки принимают `agents.max_spawn_depth` (§6).

## 4. Один авторитетный источник, хостовые адаптеры отдельно

База `skills/pdca/assets/opencode-agents/` — **единственный источник истины** для общих ролей.
Копии в оверлеях генерируются из неё, а конфиг-репозиторий хоста — **адаптер**, не ещё один
источник: никогда не копируйте роли хоста обратно в скиллы. Хостовые description, привязка
моделей по тирам и трансляция frontmatter остаются в адаптере/профиле хоста и применяются при
развёртывании агентов.

- **один пакет** — копируйте `skills/pdca/assets/opencode-agents/*.md` (или эквивалентное
  шестиролевое зеркало в `pdca-coder`/`pdca-dotnet`); если используете форму, добавьте её
  оркестратор;
- **CI-защита от дрейфа** — `python3 skills/pdca/scripts/sync_role_assets.py --check` падает на
  любом отсутствующем или разошедшемся зеркале; `--fix` пишет только пути из allowlist.
  Канонические файлы генератор не пишет.

В любом случае файлы ролей несут только метку `# tier:` и права. **Никогда не кладите `model:` в
markdown роли** — id моделей привязывает профиль хоста (§8).

> **Миграция вниз по цепочке — отдельный шаг.** Вендоринг этого исходника в конфиг-репозиторий
> **не** обновляет уже развёрнутый хост. Текущий `sync-roles` в `opencode-config` привязан к
> старому зеркалу `pdca-dotnet` и сравнивает настройки frontmatter — включая права, — а также
> **уровни** заголовков, но не текст инструкций. Несовпадение уровней ещё может быть обнаружено;
> правку только в тексте — нет, а его `--fix` сохраняет существующее тело, поэтому инструкции он
> мигрировать не может. После commit/push/вендоринга исходника тела ролей на хосте нужно
> мигрировать осознанно и перепроверить — не считайте, что `vendor-skills` или
> `sync_role_assets.py --fix` их обновили.

## 5. Поставить драйвер `pdca-orchestrator`

Драйвер — дешёвый **диспетчер**. В **автономном** режиме он ведёт один дочерний цикл, одну группу
коллекции или одну инкрементальную кампанию; в **обычном** режиме primary сам ведёт цикл, и драйвер для
него не вызывается. Он лежит в `assets/opencode-agents/` каждого скилла, поэтому шаг 3 копирует его
вместе с остальными; писать своего не нужно, и не держите рядом старую хостовую копию под тем же id.

Общие ассеты ролей записаны в **V1-карте `permission:`**, которую V2 транслирует, и каждый несёт ещё
и эквивалентный **V2-список `permissions:`**. Оба представления должны выражать одну политику; тесты
проверяют их эквивалентность. Держите оба блока синхронными при правке ассета или перегенерируйте зеркала
через `python3 skills/pdca/scripts/sync_role_assets.py --fix`.

Каким он должен быть (ассет это уже кодирует — проверьте после установки):

- `mode: subagent`, `# tier: cheap`, без `model:`;
- `edit`/`write`/`bash` (V1) или их V2-эквиваленты: **deny** — он диспетчеризует, а не работает;
- allowlist `subagent`/`task` для `pdca-planner`/`pdca-executor`/`pdca-check`/`pdca-escalate`/
  `pdca-scout`/`pdca-security-auditor` (+ необязательные специалисты `dotnet-*` и `docfx-specialist`,
  где используются), с `*` в deny;
- `skill` разрешён (он загружает контракт формы и специализированного скилла, объявленных планом).

Хост, у которого уже есть свой драйвер, может оставить его только при том же allowlist; иначе
должна победить поставляемая копия — диспетчер без `pdca-*`-allowlist цикл не запустит. Без
драйвера вообще автономный режим уходит в плоский дешёвый primary; обычный режим продолжает
работать.

## 6. Разрешить вложенную делегацию

Драйвер ведёт дочерний цикл, значит субагент должен уметь запускать субагентов. Скиллу нужна
**способность**, а не конкретный ключ: OpenCode V2 держит глубину **только** в `experimental`,
Claude Code и Codex используют свои настройки субагентов. Без неё работает описанный flat-primary
fallback. Референс OpenCode:

```jsonc
{
  "experimental": {
    "subagent_depth": 3
  }
}
```

Графу нужны не абстрактная «глубина», а **рёбра, которые реально проходит вызов**:
`primary → driver`, `driver → role` и `escalate → scout` — три ребра. В V2
`experimental.subagent_depth` считает рёбра вложенности сессий ниже основной сессии (по умолчанию
`1`), и создание дочерней сессии разрешено, только пока глубина вызывающей сессии меньше предела.
Значение — это бюджет для такого подсчёта, а не сертификат возможности: само настроенное значение
**не** доказывает, что установленная сборка поддерживает цепочку. Зафиксируйте версию установленной
сборки и полагайтесь на дымовой прогон (§9), а не на число. Значение в сниппете — пример настроенной
величины, а не проверенный бюджет.

Claude Code по умолчанию включает вложенность — три уровня ниже основной беседы — и читает
`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` из `settings.json` (`1` отключает вложенность); делегирующие
роли обязаны иметь инструмент `Agent` (§3). Как и в OpenCode, настроенный предел — бюджет, а не
доказательство работы цепочки: решает дымовой прогон.

Codex в текущем справочнике конфигурации ключа глубины не документирует: мультиагентность
включается `[agents] enabled`, веер ограничен `max_concurrent_threads_per_session`, а часть сборок
принимает `agents.max_spawn_depth`. Проверяйте установленную сборку и не выдумывайте ключ: от того,
может ли субагент запускать своих детей, зависит, возможен ли автономный драйвер вообще, и
единственное доказательство — дымовой прогон.

Top-level `subagent_depth` в V2 принимается, но **игнорируется** (предупреждение
`omitted unsupported legacy setting`), и глубина падает до одного уровня: драйвер больше не может
делегировать, и каждый автономный цикл деградирует в плоский primary. Нужен перезапуск.

## 7. Права: дать дешёвому primary диспетчеризацию

В V2 права — один упорядоченный массив `permissions`; действие для дочерних агентов —
**`subagent`** (в V1 это был `task`, и V2 транслирует конфиги, где ещё стоит `permission.task`).
`build`-primary и так всё разрешает. Primary с default-deny — `plan`, `architect` или любой
свой read-only primary — должен разрешить каждую роль явно:

```jsonc
{
  "permissions": [
    { "action": "*", "resource": "*", "effect": "deny" },
    { "action": "subagent", "resource": "pdca-scout", "effect": "allow" },
    { "action": "subagent", "resource": "pdca-planner", "effect": "allow" },
    { "action": "subagent", "resource": "pdca-executor", "effect": "allow" },
    { "action": "subagent", "resource": "pdca-check", "effect": "allow" },
    { "action": "subagent", "resource": "pdca-escalate", "effect": "allow" },
    { "action": "subagent", "resource": "pdca-security-auditor", "effect": "allow" },
    { "action": "subagent", "resource": "pdca-orchestrator", "effect": "allow" }
  ]
}
```

Все шесть id одинаковы у базы и у оверлеев (`pdca-planner`, `pdca-executor`, `pdca-check`,
`pdca-escalate`, `pdca-scout`, `pdca-security-auditor`), поэтому один allowlist обслуживает всё
семейство. Тот же allowlist нужен драйверу для своих детей — и он **не вправе** расширять права
дорогих ролей.

Если хост запрещает `general`/`explore`, обходить запрет нельзя: отсутствующая роль — это
**resource blocker** (в обычном режиме сообщается вам, в автономном — `Notice:` и записанная
причина), а не тихий прогон без роли.

## 8. Привязать модели по тирам

| Тир | Роли |
|---|---|
| cheap | `pdca-scout`, `pdca-executor`, `pdca-orchestrator` |
| medium | `pdca-planner`, `pdca-check`, `pdca-security-auditor` |
| strong | `pdca-escalate` |

Id привязываются в `agent`-блоке профиля (или в проектном конфиге), но не в роль-маркдауне:

```jsonc
{
  "agents": {
    "pdca-planner": { "model": "provider/model#high" },
    "pdca-check": { "model": "other-provider/other-model#high" },
    "pdca-executor": { "model": "cheap-provider/cheap-model" }
  }
}
```

Субагент без привязки наследует модель вызвавшего primary: работает из коробки, но весь цикл
тогда идёт на одной (обычно дорогой) модели. Для CHECK предпочтительна модель **другого
семейства**, чем у PLAN: независимый вердикт — в этом и смысл роли.

## 9. Перезапуск и проверка

Агенты читаются на старте; проверка зависит от хоста:

| Хост | Перезапуск | Проверка |
|---|---|---|
| OpenCode | `opencode service restart` | `opencode debug agents`, `opencode debug config` |
| Claude Code | правки в существующем каталоге агентов подхватываются за секунды; только что созданный каталог `agents` требует новой сессии | `/agents` перечисляет субагентов, `/tasks` показывает модель каждого, `claude plugin validate <каталог-агентов>` сообщает о frontmatter, который не парсится |
| Codex | новый тред (файлы агентов загружаются заново) | делегирование роли открывает её тред под ожидаемым `name` и показывает модель, на которой она работает; скилл `pdca` виден в списке доступных в этой сессии |
| кастомный (`dsh`, …) | по правилам хоста | аналог двух проверок ниже |

Референс OpenCode:

```sh
opencode service restart
```

Затем проверьте по порядку:

1. **Агенты видны.** `opencode debug agents` должен перечислить все роли, которые диспетчеризует
   скилл, плюс `pdca-orchestrator`.
2. **Делегация настроена.** `opencode debug config` должен показать глубину внутри `experimental`
   (предупреждение об игнорированном `subagent_depth` означает, что он лежит на верхнем уровне).
   Зафиксируйте настроенное значение, версию установленной сборки хоста и дату: само значение — не
   проверка, проверка — дымовой прогон ниже.
3. **Права развернулись.** Тот же вывод `debug agents` показывает слитый список правил по агенту:
   правила `subagent`/`edit`/`shell` должны присутствовать и идти в нужном порядке (побеждает
   последнее совпавшее).
4. **Дымовой прогон.** Запустите тривиальный цикл на одноразовой задаче. Критерии успеха: primary
   диспетчеризует `pdca-planner` (а не решает сам), `pdca-executor` пишет статус-файл в `.pdca/`, CHECK
   делает `pdca-check`, а не автор работы. Прогон должен также дать реальную цепочку делегирования,
   достигающую `escalate → scout`, на задаче, которая вызывает эскалацию. Если в статус-файле появился `Notice:` — цикл ушёл в
   fallback: читайте записанную причину, а не считайте прогон нормальным.

## 10. Preflight и fallback

Каждый лейн коллекции и каждая кампания проверяют способность **до** распределения работы.
Проверяется наблюдаемая способность, а не число в конфиге:

- разрешимы ли обязательные роли — допущены политикой, загружаются как агенты, присутствуют в
  списке агентов хоста? Проверка идёт разрешением, а не dummy substantive work: никаких пробных
  правок, пробных задач и фиктивных шагов.
- доступна ли вложенная делегация драйверу и доступен ли `pdca-orchestrator` как субагент?
- достижимо ли ребро `escalate → scout` на всех путях, где эскалация может понадобиться?
- загружается ли контракт цикла шага и не запрещён ли он?

Числа здесь не выдумываются. `experimental.subagent_depth` — факт конфигурации, а не доказательство
цепочки (§6). Ключа, элемента схемы или константы параллельного cap на стороне хоста в проверенном
исходнике V2 не найдено; это отсутствие **не** доказывает неограниченную конкурентность, и значения
`cap` тоже не выдумываются.

Установленный драйвер может **разойтись** с каноническим ассетом в
`skills/pdca/assets/opencode-agents/`. Обновите его из ассета и проверьте действующие права, прежде чем на
него полагаться: установленный `pdca-orchestrator`, не разрешающий делегирование `pdca-scout`, —
конкретный наблюдавшийся пример, и он молча ломает `escalate → scout`. Это часть чек-листа §5, а не
то, что видят тесты репозитория; остальную конфигурацию хоста менять не нужно.

Семантика отказов:

| Условие | Поведение |
|---|---|
| драйвер недоступен (нет агента, нет вложенной делегации, preflight не прошёл) | ровно один fallback: дешёвый primary ведёт inline и пишет `Notice:` с durable-причиной (в обычном режиме ещё и сообщает вам) |
| обязательная роль недоступна | resource stop: другая роль её функции не исполняет; прогон останавливается с фиксацией уже принятого |
| контракт цикла недоступен | fail closed: без подстановки «похожего» контракта и generic-исполнения |
| обнаружено поздно (после старта) | безопасная пауза до зависимого действия; правило приёмки не ослабляется |

## 11. Статус проверки: не проверено

**Статус: OPEN — prerequisite задокументирован, но невыполнен.**

Установка на чистом хосте в этом репозитории **не проверена**. Не проверены:

- установка на чистом хосте;
- выполнение `primary → driver → roles`, включая реальное делегирование, достигающее
  `escalate → scout`;
- версия установленной сборки хоста и действующие права установленных агентов;
- режим collection-lane и наблюдавшееся поведение fallback.

Успешные тесты репозитория не подтверждают установку на чистом хосте: они проверяют контракты,
ассеты и документацию, а не хост. Зелёный набор ничего не говорит о том, проходит ли цепочка на
вашем хосте.

**Триггер закрытия.** Оператор выполняет разрешённый запуск на чистом хосте и фиксирует:

- фактическую версию/сборку хоста и дату выполнения;
- доступность всех шести обязательных ролей;
- режим collection-lane и наблюдавшееся поведение fallback;
- реальную цепочку делегирования, достигающую `escalate → scout`;
- результаты выполнения и подтверждающие журналы.

Отдельный последующий цикл записывает эти свидетельства на эту страницу. Только этот цикл может
сменить статус с OPEN; завершение шага здесь или зелёный прогон репозитория этого не делают.

## 12. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| Роль «не найдена» при диспетче | нет файла агента, или он лежит в каталоге, который хост не сканирует | положить в `~/.config/opencode/agents/` (или `.opencode/agents/`), перезапустить, сверить `debug agents` |
| Цикл ушёл в плоский primary | нет `pdca-orchestrator`, нет рабочей вложенной делегации (legacy-ключ игнорируется, предел слишком мал), либо хост запрещает делегацию | §5 и §6 |
| `Notice:` об отсутствующей роли | имя роли в скилле не совпадает с именем установленного агента (например, `pdca-planner` vs `pdca-planner`) | поставить соответствующее семейство или завести алиас |
| Роль ведёт себя как V1-двойник | в ассете есть и `permission:`, и `permissions:`, и один из блоков устарел | держите оба блока семантически эквивалентными (и перегенерируйте зеркала `sync_role_assets.py --fix`); V2 транслирует `permission` → `permissions`, `task` → `subagent`, `bash` → `shell`, `write`/`patch` → `edit`; слитые правила видны в `debug agents` |
| Правило ни на что не влияет | в ассете действие вне списка V2 Core | `todowrite`, `doom_loop` и `list` не входят в V2 Core-действия прав (плагины могут определять свои). Они проходят через конфиг, но ни с одним встроенным инструментом не совпадают. Безвредно, но полагаться на них нельзя |
| Сбор фактов идёт на дорогой модели | в профиле нет привязки тира | §8 |
| Чтение `.pdca/` уходит в `ask` | хост запрещает `.pdca/**` для `pdca-check`/`executor` | разрешить `read`/`edit` на `.pdca/**` этим агентам |

## 13. Чего эта настройка не делает

- Не выбирает и не привязывает модели; без тировых биндингов роли наследуют модель primary (§8).
- Не даёт прав на коммит и merge. `pdca-collection` нужен явный проектный overlay или ваша
  просьба для `git merge --no-ff`; без этого группа идёт без коммитов и помечается `incomplete`.
  Push не даётся никогда.
- Не расширяет права для автономного режима. Автономность снимает вопросы, а не правило приёмки,
  требования к доказательствам или границы прав.

## 14. Пусть агент установит сам

Чек-лист упакован в промпт: [`install-prompt.md`](../install-prompt.md). Заполните блок `Inputs` —
включая `HOST=opencode|claude|codex|dsh|custom` — отдайте дешёвому primary (например `build`);
агент выполнит шаги идемпотентно, с бэкапами, перезапуском и проверкой из §9.

Нормативный источник остаётся за файлами скиллов: `skills/<skill>/SKILL.md`, раздел
`## Roles and host requirements`.
