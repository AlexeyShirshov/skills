# Кейс для статьи: PDCA Collection — слияние без конфликта, шесть ошибок компиляции (Nextorm 1.0.9-rc4)

> **Назначение:** факты, хронология, цифры и ссылки для самостоятельного написания авторской прозы. Это **не готовый фрагмент статьи**. Вставлять в [черновик](pdca-incremental-collection-article-draft.md) логично в § «PDCA Collection → Интеграция». Данные зафиксированы по тегу релиза `v1.0.9-rc4`, а не по меняющейся ветке `main`.

## Сюжет и основной смысл

- **Предмет:** автономное выполнение набора задач релиза 1.0.9-rc4 через `pdca-collection`.
- **Проблема:** успешно принятые по отдельности изменения перестали быть совместимыми после объединения двух веток. Git не нашёл текстового конфликта, но сборка выявила несовместимость.
- **Почему это важно для статьи:** локальный CHECK конкретного пункта, корректное слияние Git и CHECK объединённого результата — три разные проверки. Первые две не заменяют третью.
- **Центральный эпизод:** интеграция изменений SQL Server по issue **#282** (в коллекции также фигурирует пункт `T348`).

## Техническое ядро эпизода

**До параллельного изменения (фрагменты, концептуально):**

```csharp
switch (node.Method.Name)
{
    case nameof(SomeSqlServerAggregate):
        // реализация новой функции
        break;
}
```

**После изменения в основной ветке (фрагменты, концептуально):**

```csharp
switch (Classify(node))
{
    // здесь требуются значения enum, а не имена методов
}
```

> Сниппеты выше — **схематическое пояснение по журналу**, не дословная копия исходного файла. Если для статьи потребуется настоящий diff, отдельно извлечь его из коммита `a28bb852` или соответствующего PR/изменения.

**Причина ошибки:** Git сопоставляет изменения текста; компилятор проверяет их совместимость как единой программы. Текстовая непротиворечивость не гарантирует семантическую.

**Подтверждение повторяемости:** в том же журнале описан похожий случай с PostgreSQL (`T347`, связь с #281): **3 ошибки `CS0029`** по тому же механизму. Это полезное дополнительное свидетельство, но **основным кейсом остаётся #282**, чтобы статья не распадалась на несколько историй. [Запись о повторном случае][rc4-second].

## Числа, которые можно безопасно использовать

- **56/56** — исходные подготовленные пункты при первом ALL-barrier, **не** число завершённых задач.
- **9 групп / 4 линии** — первоначальное расписание, **не** неизменный состав коллекции до конца релиза.
- **6 × CS0029** — ошибки компиляции после бесконфликтного объединения #282.
- **6 элементов enum + 6 отображений Classify** — адаптация для объединённого кода.
- **85 новых тестовых строк** по SQL Server прошли по новому пути; **1736 → 1821** — счётчики проверок по записи журнала.
- В срезе статус-файла на теге `v1.0.9-rc4` присутствует сводка **66/79 `done`**, **`Verified: —`**, часть работы ещё открыта. Это **не** отчёт о полном `done` коллекции. [Сводка][rc4-status-end].

## Предлагаемый порядок раскрытия автором (не готовая проза)

1. Коротко задать масштаб: бэклог релиза, готовые планы, группы и параллельные линии.
2. Пояснить, что у каждой задачи есть своя локальная приёмка.
3. Дать конкретную проблему: две ветки независимо меняют один механизм, причём по разным строкам.
4. Показать разницу между успешным Git merge и неуспешной сборкой (6 × `CS0029`).
5. Объяснить исправление и зачем нужен отдельный интеграционный CHECK объединённого дерева.
6. Сохранить оговорку: локальное исправление кейса **не означает** полного завершения всей коллекции.

## Границы утверждений и проверка перед публикацией

- **Не утверждать**, что все пункты коллекции были завершены или что релиз был полностью проверен именно в момент слияния #282.
- **Не смешивать** исходные 56 подготовленных задач и более поздние 79 строк сводки — состав расширялся по ходу исполнения.
- **Не называть** семантическую ошибку «конфликтом Git»: наоборот, смысл истории в **отсутствии текстового конфликта**.
- Не приписывать скиллу гарантированное ускорение разработки: этот кейс показывает сохранение проверяемости, а не измерение экономии.
- Основная статья уже описывает интеграцию; достаточно **одной короткой практической вставки**, а не пересказа всего status-файла.
