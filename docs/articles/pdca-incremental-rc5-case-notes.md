# Кейс для статьи: PDCA Incremental — кампания покрытия до 80% (Nextorm 1.0.9-rc5)

> **Назначение:** источниковедческие заметки, цифры и хронология для самостоятельного написания авторской прозы. Это **не готовый текст статьи**. Логичное место в [черновике](pdca-incremental-collection-article-draft.md) — «PDCA Incremental → Пример». Источники зафиксированы по тегу `v1.0.9-rc5`, чтобы результаты не зависели от обновления `main`.

## Сюжет и основной смысл

- **Исходное задание:** GitHub issue **#364**, достичь **не менее 80% branch coverage** интеграционными тестами Nextorm (без unit-тестов) и, **после достижения цели**, изменить порог CI на **78%**.
- **Форма работы доказана статусом:** `Form: incremental`, `Mode: autonomous`, несколько последовательных проверяемых шагов PDCA.
- **Неизвестность:** заранее неясно, сколько новых тестов можно написать, какие ветви реально достижимы интеграционным способом и насколько результативны предполагаемые направления.
- **Главная особенность:** каждый замер менял представление о проблеме и влиял на следующий шаг. Кампания завершилась **не достижением 80%**, а обоснованной фиксацией границы результата и решением владельца.

## Условия измерения и исходная точка

| Параметр | Подтверждённое значение |
| --- | --- |
| Метрика | `Branch coverage` из отчёта `Summary.txt` (`reportgenerator`), доля покрытых ветвей |
| Объём | Только `tests/nextorm.integration.tests`, восемь сборок; фильтр `-NextORM.Core.InMemory*`; unit-тесты не учитываются |
| Цель кампании | **≥ 80,0%**; первоначально после достижения изменить порог CI **74 → 78%** |
| Начальное измерение (baseline) | **38 814 / 52 131 = 74,4%** |
| Характер baseline | Измерение принято **с ограничениями**: полный прогон имел **9 падений**, `rc=2`; нельзя называть его полностью зелёным |
| Источник | [Шапка кампании][inc-header], [baseline record][inc-baseline], [исходная задача][inc-original] |

**Техническая точность:** метод измерения определяется при входном PLAN/подготовке. Сам baseline получен и проверен **первым шагом кампании** (DO → CHECK → ACT), а не произвольным замером внутри PLAN.

## Шаги кампании (смысл, не полный отчёт)

| Шаг | Предмет | Что полезно показать автору |
| --- | --- | --- |
| **1 — baseline** | Полный исходный замер `74,4%` | Сначала фиксируется единая база для дальнейших сопоставимых измерений. Knowledge-инкремент принят, прирост покрытия = 0. |
| **2 — функции провайдеров** | Работа с тестами PostgreSQL, MySQL, MariaDB, SQL Server | Выявлена ограниченная отдача направления. Продуктовый инкремент не был принят независимым CHECK; полезное знание о насыщении семейства сохранено для следующего решения. |
| **3 — ядро/SQLite/EF Core** | Переход к более перспективным классам и проверка предполагаемой отдачи | Реальная конверсия оказалась заметно ниже прогноза (в журнале около **20%**); следующее действие выбиралось на основании измерений, а не первоначального ожидания. |
| **4 — дополнительный тестовый батч** | Добавление проверок и пересмотр доказательств | Владелец **явно принял ограниченный результат** при сохранившемся независимом вердикте `CHECK not accepted`; нельзя называть этот шаг безусловным PASS. |
| **5 — feasibility probe** | Исследование остатка: какие ветви достижимы, какие нет и насколько реалистична цель | Проверка гипотезы о достижимости предшествовала следующей большой попытке; не вся ценность инкремента обязательно выражается в новом коде. |
| **6 — итоговый батч** | Доработка тестов, уточнение знаменателя, повторный замер | Достигнут измеренный итог **75,6%**; целевые 80% остались недостижимыми в пределах принятых ограничений. |

[Шаги и решения в шапке статуса][inc-header]; [финальное закрытие][inc-closure].

## Числа для статьи — проверенные

| Показатель | Исходно | На момент закрытия |
| --- | --- | --- |
| Branch coverage | **74,4%** | **75,6%** |
| Покрытые ветви | **38 814** | **39 595** |
| Общее количество учитываемых ветвей | **52 131** | **52 349** |
| До целевых 80% | исходно требовалось 80% | **2 285 покрытых ветвей не хватило** при финальном знаменателе |
| Порог CI | **74%** | **75%** по решению владельца вместо первоначально предполагаемых 78% |

Дополнительно из итогового отчёта:

- Число покрытых ветвей увеличилось на **781**, а знаменатель изменился на **+218**. Сравнивать только проценты без учёта дрейфа знаменателя некорректно.
- За время кампании затронуто **51 тестовое файлa**: 33 в одном и 18 в другом коммите (это цифры из итогового отчёта; не делать вывод о числе *новых* тестов без отдельного подсчёта).
- **6 in-memory-only методов** выведены из учитываемого покрытия; эффект на знаменатель — **−92 ветви**. Это ограниченное изменение по явному решению владельца, а не разрешение скрывать произвольные непокрытые ветви.
- Разбор остатка: `R = 2 696` (достижимые), `U = 3 541` (недостижимые), `? = 4 012` (неустановленные). После вычета доказанно недостижимых `R_corrected = 2 514`; дефицит **2 285** потребовал бы закрытия приблизительно **90%** этого пула.
- Первый прицельный батч по крупнейшему живому блоку `SelectGroup` дал **36 условий из 454** ранее непокрытых — порядка **8%**. Это аргумент в пользу оценки убывающей отдачи, а не гарантия, что других методов достичь цели нет.
- Финальный интеграционный прогон **не был полностью зелёным**: `rc=2`, 7 падений ClickHouse. Не изображать итог как «все тесты успешно прошли».

Все пункты — [фактическое завершение кампании][inc-closure] и [записи baseline / ограничений][inc-baseline].

## Итог и важнейшее разграничение

- **Кампания:** в финале стоит **`Status: closed (incomplete)`**, потому что исходная цель **80% не достигнута**.
- **Решение владельца:** «ок, давай фиксируем 75 в CI и закрываем задачу». Порог CI повышен **74 → 75**; issue #364 закрыт с отчётом.
- **Это разные факты:** закрытие GitHub-задачи по решению владельца **не означает** принятия исходной цели Incremental. Нельзя писать «Incremental довёл покрытие до 80%» или «кампания завершилась успехом».
- **Что действительно показано:** измеримый прирост, проверяемое движение, принятие знаний от неудачных направлений, сохранение доказательств, сознательное прекращение работы без маскировки недостигнутой цели.

Источники: [итоговый отчёт][inc-closure], [статус кампании][inc-header].

## Предлагаемый порядок раскрытия автором (не готовая проза)

1. Задать исходную цель: «поднять покрытие до 80%» — известно **что**, неизвестно **сколько шагов и каких**.
2. Указать измеримый baseline **74,4%** и стабильную методику измерения.
3. Показать, как первые батчи тестов дали информацию об ограниченной отдаче выбранных направлений.
4. Пояснить поворот к исследованию достижимого покрытия и дрейфа знаменателя; можно упомянуть feasibility probe.
5. Привести реальный результат **75,6%**, число затронутых файлов и открытый остаток **2 285 ветвей**.
6. Чётко развести **решение закрыть issue** и **статус `incomplete` исходной кампании**.
7. Связать наблюдение с назначением Incremental: серия независимых CHECK и следующих шагов, опирающихся на принятые факты.

## Что не утверждать

- Не выдавать серию обычных циклов за кампанию: здесь режим **явно подтверждён** строкой `Form: incremental`.
- Не писать, что цель 80% достигнута; **75,6%** — действительный результат.
- Не писать, что **78%** попали в CI; фактически порог изменён до **75%**.
- Не представлять все промежуточные проверки зелёными и не приписывать продуктовый успех шагам, которые дали только знания или были приняты владельцем с оговорками.
- Не трактовать закрытие issue как независимый `whole-goal CHECK: PASS`.
- Не объявлять техническую невозможность 80% вообще: вывод относится к **исходным ограничениям и измеренной экономике дальнейших шагов**, а не ко всем мыслимым будущим изменениям проекта.
